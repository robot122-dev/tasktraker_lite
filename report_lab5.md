# Лабораторная работа №5. Настройка простого CI/CD-пайплайна

## Цель работы

Настройка непрерывной интеграции и доставки (CI/CD) для веб-приложения TaskTracker Lite с использованием GitHub Actions и автоматической публикации на GitHub Pages.

---

## 1. Создание репозитория с веб-приложением

Проект TaskTracker Lite реализован как одностраничное веб-приложение на HTML5, CSS3 и JavaScript. Приложение позволяет пользователю добавлять задачи, удалять их, изменять статус (К выполнению → В работе → Выполнено), фильтровать по статусу и искать по названию/описанию.

### Структура проекта

Таблица 5.1 — Файлы проекта TaskTracker Lite

| Файл | Назначение |
|------|------------|
| `index.html` | Главная страница приложения |
| `css/style.css` | Стили интерфейса |
| `js/tasks.js` | Модуль логики работы с задачами (чистые функции) |
| `js/app.js` | Модуль взаимодействия с DOM (рендеринг, обработчики событий) |
| `__tests__/tasks.test.js` | Unit-тесты модуля tasks.js |
| `package.json` | Метаданные проекта и зависимости |
| `jest.config.js` | Конфигурация тестового фреймворка Jest |
| `.github/workflows/ci.yml` | Конфигурация CI/CD-пайплайна GitHub Actions |
| `.gitignore` | Список файлов, исключённых из контроля версий |

### Архитектура приложения

Логика приложения разделена на два слоя:

- **`tasks.js`** — модуль чистых функций, отвечающий за бизнес-логику: создание, удаление, изменение статуса, фильтрация и поиск задач. Этот модуль тестируется с помощью Jest.
- **`app.js`** — модуль представления, отвечающий за отрисовку DOM, обработку событий пользователя и сохранение данных в `localStorage`.

Такое разделение позволяет тестировать бизнес-логику изолированно от интерфейса, что является хорошей практикой при организации unit-тестов.

## 3. Настройка GitHub Actions

CI/CD-пайплайн настроен в файле `.github/workflows/ci.yml`. Workflow запускается автоматически при пуше и создании pull request в ветки `main` или `master`.

### Этапы пайплайна

**Job 1: Тесты (`test`)**
1. **Checkout** — клонирование репозитория с помощью `actions/checkout@v4`.
2. **Setup Node.js** — установка Node.js версии 20 с кешированием npm (`actions/setup-node@v4`).
3. **Установка зависимостей** — выполнение `npm ci` для восстановления зависимостей из `package-lock.json`.
4. **Запуск тестов** — выполнение команды `npm test` (Jest).

**Job 2: Сборка (`build`)**
1. **Checkout** — клонирование репозитория.
2. **Setup Node.js** — установка Node.js.
3. **Установка зависимостей** — `npm ci`.
4. **Сборка проекта** — копирование файлов приложения в директорию `dist/`.
5. **Загрузка артефакта** — использование `actions/upload-pages-artifact@v3` для подготовки к деплою.

**Job 3: Деплой на GitHub Pages (`deploy`)**
1. Запускается только при пуше в `main` или `master`.
2. Использует `actions/deploy-pages@v4` для публикации содержимого `dist/` на GitHub Pages.

### Структура workflow

Таблица 5.3 — Этапы CI/CD-пайплайна

| Этап | Действие | Описание |
|------|----------|----------|
| Checkout | `actions/checkout@v4` | Клонирование репозитория |
| Setup Node.js | `actions/setup-node@v4` | Установка среды Node.js 20 |
| Install dependencies | `npm ci` | Установка зависимостей |
| Run tests | `npm test` | Запуск Jest-тестов |
| Build | `mkdir -p dist && cp ...` | Сборка статических файлов |
| Upload artifact | `actions/upload-pages-artifact@v3` | Подготовка к деплою |
| Deploy | `actions/deploy-pages@v4` | Публикация на GitHub Pages |

### Неуспешный запуск с ошибкой теста

Если в коде допущена ошибка, приводящая к провалу теста, пайплайн останавливается на этапе тестов. Job-ы сборки и деплоя не выполняются.

Пример ошибки: изменение функции `getNextStatus` так, чтобы она возвращала `'done'` вместо `'in_progress'` после `'todo'`.
